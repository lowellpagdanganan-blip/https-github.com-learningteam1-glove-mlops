# Monitoring Findings — glove_fail_classifier

**Reference:** clean training data (800 rows). **Current:** simulated recent
production sample (400 rows). Generated by `python monitoring/run_report.py`.

## Headline

**5 of 11 feature columns drifted (share 0.417).** The dataset-level drift flag
stays *below* Evidently's 0.5 threshold, so this reads as an **early-warning
signal**, not a full-dataset drift alarm. The 4-test data-quality suite passed
(no missing values, no malformed rows).

## What drifted, and why it matters

The simulated production sample represents an older, more heavily-used glove
fleet than the training population. The drifted columns line up with that story:

| Feature | Shift (reference to current) | Meaning |
|---|---|---|
| `Age_as_of_Test` | mean ~2.0 to ~4.8 yrs | Fleet in service is older. |
| `Usage_Rate` | mean ~815 to ~1272 | Gloves used more intensively per year. |
| `Liveline_Ratio` | mean ~0.56 to ~0.70 | Higher share of live-line exposure. |
| `Number_of_Owners` | shifted up | Gloves passed through more hands. |
| `Test_Year` | shifted to later years | Recency shift in the sample. |

These are precisely the **usage-based engineered features** the model leans on
to predict failure, so drift concentrated here is higher-risk than drift in a
static field would be: it sits where the model is most sensitive.

## Is the model still trustworthy?

Data drift alone does **not** prove the model is wrong — it proves the incoming
data no longer matches what the model learned from. Two cases:

1. **Relationship still holds** — older, more-used gloves still fail more, and
   the model copes. Confirm via prediction/target drift and, once physical
   re-test labels arrive, live accuracy.
2. **Relationship moved** (concept drift) — if newer glove batches behave
   differently, the learned boundary is stale and accuracy will fall.

Input drift alone can't distinguish these, which is why the report includes
target drift and why the recommendation below is label-driven.

## Recommended actions

1. **Do not auto-retrain on drift alone** — retraining on drifted-but-unlabeled
   data can bake in the shift. Wait for re-test ground truth.
2. **Raise a review, not an outage.** The endpoint keeps serving; a drift alert
   should notify the team, not block predictions.
3. **Backfill labels** from the physical dielectric re-tests, recompute accuracy
   on the recent slice, and retrain only if it drops below the agreed threshold.
4. **Wire the current dataset to real logged `/predict` inputs** so this runs on
   production traffic instead of a simulated sample.
